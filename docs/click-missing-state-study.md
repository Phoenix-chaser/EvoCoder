# 公开测试只覆盖开启状态时，技能修订能补上什么

这项实验考察 Coding Agent 能否在公开测试遗漏一种状态时，为真实 CLI 编写可执行的检查，再把失败中学到的方法用于下一次修复。父子版本使用相同的模型、工具、行动预算和运行环境。

## 先复现第 7 步的错误

上一版技能在第 7 步写入了一个历史例子，声称进度条在同次修改后出现“开启通过、关闭失败”。其引用池有三条运行。进度条任务相关运行共四次公开测试，没有一次同时记录这两个结果。观察 22 在同一源码快照上记录的是两态均失败。

新提案由模型选择条件、操作、目标、观察量和顺序。程序把这些字段渲染成步骤。要陈述历史测试结果，模型还须引用学习运行、该次测试的序号和完整两态结果。提案注册时核对事件的补丁与输出哈希。缺少命名测试时，对应状态为未报告。原始自由文本与错配状态都被拒绝，临时数据库新增技能均为零。输入同一事件真实记录的两态均失败作为正对照时，成功新增一条技能。

新检出的仓库可用标准库核对随附样本。重跑生产提案注册路径需要原实验归档。

~~~bash
python3 scripts/verify_step_example.py
uv run --locked python scripts/verify_step_admission.py --previous experiments/glm-click-procedure-002 --output /tmp/evocoder-admission.json
~~~

## 单状态学习题

| 真实上游修复 | 唯一公开 CLI 用例 | 独立评测中的对应边界 | 缺陷版本的公开结果 |
| --- | --- | --- | --- |
| 带颜色的输入提示和确认 | 显式开启颜色，确认提示保留 ANSI | 关闭颜色后，对话文本应去除 ANSI | 通过 |
| Bash 选项补全 | 区分大小写时，按枚举成员名补全 | 忽略大小写时，输出规范化的小写候选 | 失败 |
| 进度条当前项目标签 | 设置回调时，显示当前正在处理的项目 | 关闭项目标签时，不应泄漏原始项目值 | 失败 |

三题均来自 Click 的实际修复。每题在修复前都能复现独立测试失败，上游修复均通过公开与独立测试。任务 ID、缺陷组、上游提交、补丁指纹和有记录的变更函数都与既有清单去重。同仓库的源码与依赖仍有重合。[颜色处理](https://github.com/pallets/click/commit/93ba0075f4881b858b61f89a753c7c10e330027e) · [Bash 补全](https://github.com/pallets/click/commit/32ae2acd3474a57d2450ea849545b2e1258bf76a) · [进度条标签](https://github.com/pallets/click/commit/2ba2fe0cf80a76e09a6e44c3750034574acd33d0)

模型看到问题描述、源码和一个开启用例。上游修复、私有测试和关闭变体由评测器保管。CLI 脚本的内容由求解模型当场生成。父子都可以选用相同的新工具，也可以照常执行普通命令。

## 如何证明检查有效

1. 把模型动作与紧随其后的运行观察配对，保存脚本、当时可编辑的源码、执行参数、镜像、输出和退出码。
2. 在无网络 Docker 中，以动作发生时的补丁、上游修复，以及仅破坏对应关闭行为的变体分别重放脚本。观察器记录本地 Click 的实际 CLI 调用和返回值。
3. 原动作退出状态可复验，脚本在上游修复通过，在关闭变体上因自己的断言失败，且相应 CLI 输出或状态发生变化，这条执行才取得“捕捉关闭回归”的判定。
4. 同一运行写多条脚本时按运行去重。只打印结果、导入失败、直接跑控制方测试、只比较源码文本，均不计入关闭回归检测。依赖临时文件或绕过当前观察器的普通命令标为尚未证实。单个合成变体覆盖一个特定回归，整题另有独立评分。

关闭变体及其正负对照在首次 GLM 调用之前已校准。学习题的变体都保留公开开启用例通过，并导致独立关闭用例失败。Click #557 的变体只破坏禁止帮助选项时的提示。计数选项题的变体破坏普通数值选项的两种显式范围显示，保留计数选项的参考行为。

## 何时可以谈收益

学习时固定注入父版。提案只能引用本批次实际应用父技能后出现的失败。模型选择操作步骤，系统掌握可选操作与历史事实的表达形式。子版冻结后先固定回放学习题，再用计数选项和 Click #557 做正常路由配对。每题两次，交替父子顺序。另行预登记固定注入对照，用于区分路由选择和技能正文的作用。

门禁要求至少两个独立开发组，在两次配对中都出现与技能有关的改善，且没有回归或基础设施错误。即使其余开发组全胜也不能达标时，提前结束。通过后再验证其他开发题、历史回归和支持案例，最后才动用两道留出题。反复使用过的开发题主要用于诊断。自写检查能检出某个回归、完成整题修复和在新题上稳定提高修复率，需要分别给出证据。

## 这次正常路由对照得到了什么

父版为 4a88b651b305，子版为 9dd9edc98d84。子版只引用颜色题上的一次父版失败。该补丁通过了公开测试。事后重跑五项独立检查，确认文本开颜色、普通提示关颜色，以及普通无色交互共三项通过；确认文本关颜色、普通提示开颜色两项失败。提案阶段收到的是独立评分结果与公开轨迹，分支明细只用于事后诊断。

GLM 生成了十二条有序步骤。第 3 步要求在公开覆盖不足时自写两态 CLI 检查，第 7 步要求修改后重跑。新技能中的历史陈述只引用观察 32，该次公开测试记录为开启通过、关闭未报告。在三道学习题上，父子独立评分均为 2/3。父版在颜色题提交未达标补丁，子版用完 16 步。子版的第一条修改源码指令被模型放在“修改后”条件下，这个顺序值得在后续学习中检验。

| 已通过独立测试的次数 | 计数选项，父／子 | Click #557，父／子 | 总计，父／子 |
| --- | --- | --- | --- |
| 正常路由，各重复两次 | 1/2 · 2/2 | 2/2 · 1/2 | 3/4 · 3/4 |
| 固定注入，各重复两次 | 2/2 · 2/2 | 1/2 · 2/2 | 3/4 · 4/4 |

所有八次正常路由均实际注入相应技能。计数选项第一次配对子版胜、第二次两版均通过。Click #557 第一次两版均通过、第二次子版退化。重复确认的改善组为零，触发门禁提前停止。两道留出题的模型调用为零。含学习、提案、学习回放及正常路由对照的主实验总账记录 208 次请求，按本地计量配置结算 561.56253 套餐积分，另有 74.67168 积分预留。两次 HTTP 429 的中断尝试单独留存，均未纳入修复评分。

固定注入的四对实验额外记录了 101 次请求，结算 258.32105 套餐积分。三对均为两版通过，Click #557 第二对为父版失败、子版通过。该题在正常路由中的第二对结果方向相反。正常路由的八次也都注入了技能，两种策略是独立采样，仅凭这组结果无法把波动归因于路由选择。

## 为什么“写了关闭断言”和“能发现关闭回归”得到不同的数

在动作发生时的补丁上，父版有 2/3 道学习题能复现相应关闭调用，子版为 3/3。两版在学习题上检出预先校准的关闭回归均为 0/3。这些数字按学习运行去重。在子版生成后、首个开发对照开始前，额外登记了调用到达条件。核验器比对原动作的退出码与输出哈希，并要求原补丁、上游修复和关闭变体实际到达同一脚本位置、同一组 CLI 输入。

Bash 补全的子版在脚本第 17 行写了关闭大小写敏感后应返回小写候选的断言。第 15 行先断言某个无匹配调用输出必须是空串。这个较早的断言连上游修复也无法通过。随后的打印脚本使 GLM 看到了关闭状态的输出，却没有断言会对错误结果报警。颜色题的子版也实际调用了两态，只打印结果。复演把这些观察与能检出变体的检查分开计数。

在四次正常路由的开发配对中，父子各有一次自写检查能检出对应边界回归。子版第一次赢下计数题时没有发送自写脚本；第二次计数题才有有效断言，而父子都通过了。一次配对胜利不能归因于这条新增验证步骤。

计数题首轮父版耗尽行动预算，没有提交补丁；子版提交的补丁与上游公开行为一致。Click #557 第二次的子版补丁通过了公开测试。事后用禁用帮助选项的命令调用它，退出码仍为预期的 2，却多打印了建议用户运行不存在的 --help 选项的一行。该反例解释了正常路由记录的一次退化。

## 同一学习补丁上的两次针对性验证

补测只访问已用过的 Bash 补全学习题。先按公开轨迹选取父版和子版最后一条实际触发 AssertionError 的脚本。给 GLM 原脚本、原报错和问题描述，限定每条轨迹至多三次检查动作。父版用一次、子版用三次，最后都得到退出码 0 的脚本，但两个全绿脚本都只调用了 case_sensitive=True，均未检出关闭回归。

随后添加针对 Click Bash 补全的运行时覆盖反馈。控制器从公开示例读取开启值，从两个全绿脚本的真实 CLI 调用读取实际开关值，明确指出缺少 False。模型在原补丁上各有一次机会自行编写检查。两次都生成了小写补全记录断言，均在原补丁和上游修复上返回 0，在关闭行为被破坏时返回 1。父版轨迹的断言在脚本第 10 行失败，子版轨迹在第 14 行失败。预期记录字符串由 GLM 写出，控制器只提供公开的状态差异。

| 同一 Bash 学习题上的检查 | 父版轨迹 | 子版轨迹 |
| --- | --- | --- |
| 普通定向补测后能检出关闭变体 | 否 | 否 |
| 增加实测覆盖反馈后能检出关闭变体 | 是 | 是 |

后一项验证涉及同一学习题的两份补丁。两组都获得额外预算和明确的缺失状态反馈，数据支持这个检查修复工具在此案例上有效。它与原始技能的主动执行能力、正常路由评分和留出集收益分别统计。

主实验、固定注入、普通定向补测、带覆盖反馈的补测合计 315 次真实 GLM 请求。各阶段分别结算 561.56253、258.32105、8.92222、2.66703 套餐积分，按本地账本合计 831.47283。另有 74.67168 积分未决预留。Docker 离线审计不调用模型。

## 离线复验

仓库内的两个样本都可以直接用 Python 标准库核对。第二条命令展示同一份学习补丁上，原始求解脚本、普通定向补测和增加覆盖反馈后各自取得的判定。

~~~bash
python3 scripts/verify_step_example.py
python3 scripts/replay_click_example.py
~~~

已有本次实验镜像和 Click 镜像仓库的机器可以重放真正的 CLI 调用。程序从固定提交恢复原始源码，重建发生模型动作时的补丁，再对比当时的源码、上游修复和关闭变体。该过程不调用模型。

~~~bash
uv run --locked python scripts/replay_click_example.py --click-git work/upstream/click.git
~~~

新机器可先获取 Click 的 Git 镜像并运行 make comparison-image，再传入 --image evocoder-comparison:py312-v1。报告区分原镜像重放与其他本地镜像上的行为一致性检查。

完整归档的复核入口如下。在主实验目录存在时，导出器逐条复算学习证据、正常路由门禁和用量，并复演自写的 CLI 检查。

~~~bash
uv run --locked python scripts/report_click_procedure.py --root experiments/glm-click-missing-state-001 --output /tmp/evocoder-missing-state-report
~~~
