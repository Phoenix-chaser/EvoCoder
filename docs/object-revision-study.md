# 一次漏修能让技能学会处理调用方对象吗？

上一轮在三道对象开发题上各做两轮，人工技能修好 6/6，强制使用 GLM 学得的父版修好 2/6。正常路由从未选中父版。我们把这个现象当作选题线索，保留原对象面板和 30 道封存的配置题，另建六个学习仓库。两个子版都由 GLM-5.3 从同一父版生成，各自冻结后再评分。下面所有修复数都来自提交补丁的独立评分。[原对象实验](falsy-transfer-study.md) · [首轮预登记](../benchmarks/falsy_transfer/object-revision.json) · [补充预登记](../benchmarks/falsy_transfer/object-witness.json)

## 实际失败来自哪里

六个独立编写的 Python 学习题涉及瓦片混色器、调度时钟、撤销日志、流解码器、依赖遍历集合和通知租约。一个合法对象可能因为暂时没有数据而求值为假。原始缺陷版在六题上都通过常规对照，又都未通过公开复现和相应的两个对象检查。每题的参考修复通过全部检查。学习题、开发题和留出题之间的源码组均已冻结。[可执行任务和参考修复](../scripts/object_revision_cases.py)

每题安排一次正常路由和两次强制使用父版的尝试，首轮交错两组的运行顺序。每次都有 15 次求解动作。正常路由六次都未注入父版，六次都修好。强制使用父版的 12 次中修好 11 次。唯一一次失败发生在通知租约学习题的第二次强制尝试。模型交付的补丁能在直接发送时使用借入的租约，公开测试与常规对照也通过了。但是延迟重投时，一个布尔值为假的借入租约仍会被替换。此前在同一快照上、同样强制使用父技能的另一次提交，通过了这一检查。[学习运行、补丁哈希与复验](results/object-revision.json)

## 同一个父版为什么产生了两个不同的子版

**首个子版**从三条学习运行修订，依据包括这次失败、同题跳过技能后成功的运行，以及另一道题上使用父版成功的运行。提案器看得到公开问题、补丁差异和已核对的测试收据，独立评分只告诉它最终是否通过。模型增加了检查重试等其他入口的步骤，却把正向条件限定为单一入口的配置适配器，并将资源管理对象写入排除项。它形成了真实的新版本。[首个子版与证据绑定](results/object-revision.json)

**补充实验**在看到首个子版的内容和部分开发结果后另行登记。我们回到同一个父版，取同题两次强制使用父版、公开都通过但最终结果不同的真实补丁。GLM 看两个匿名补丁、原问题和公开示例，自己写可直接执行的 Python 断言。它看不到两个补丁的成绩、参考修复、隐藏测试、人工技能或开发记录。每条断言在三个独立 Docker 工作区运行。只有在漏修补丁上产生断言失败、在另一个实际补丁和参考修复上通过，才能用作修订证据。[断言生成与执行](../scripts/object_witness.py)

三次尝试中，第一次在漏修补丁上发生其他运行异常，第二次未通过检查程序的格式或访问约束，第三次获得预先规定的三份结果。第三个程序复用了公开示例的租约形状，自行组合了直接发送、暂存、重投与缺省租约的对照。它断言重投继续使用同一借入对象，进入和退出次数正确，而且服务没有额外打开租约。公开归档包含该程序以及它区分的两个合成学习补丁。[补充实验的原始观测](results/object-witness.json)

第二个提案器还看到同一父版在其他三道对象学习题上成功的记录。它的第一次输出引用了冻结池以外的运行，系统拒绝了该提案。按预登记使用同样的输入重试后，GLM 将时钟、日志、管理器等调用方提供的对象加入了适用条件，并要求沿调用链追踪对象身份，在确实缺失时才获取默认资源。这个版本与首个子版是兄弟版本。两次提案的证据组合和提示均有变化，因此无法单独估算新增断言对修订内容的因果贡献。[模型生成内容、证据与费用](results/object-witness.json)

冻结第二个子版后，我们用正常路由重新求解六道学习题。父版先前是 **0/6 次注入、6/6 次修好**，新子版是 **5/6 次注入、6/6 次修好**。它被选用于瓦片混色、调度时钟、撤销日志、流解码和通知租约，跳过了依赖遍历集合。这六次求解发生在提案之后，均以评测身份运行。这给出了适用范围确实改变的行为证据。学习题上，两组的修复数相同。[逐题路由与补丁复验](results/object-witness.json)

## 怎样判断修订带来了收益

两个子版各自回打相同的开发快照，每题两轮，第二轮反转各组运行顺序。对象题重跑无技能、正常路由父版、正常路由子版、强制父版、强制子版及人工参照六组。配置题重跑前三组。两种子版分别使用当次的对照。所有组各有 15 次求解动作，正常路由额外使用一个模型步骤。强制组检验技能文本在实际注入时能否帮助修复。正式发布使用正常路由。[实验执行器](../scripts/run_object_revision.py)

发布须同时满足原对象面板的正常父子门禁、全部七道开发题与学习证据回放的正常父子门禁，以及相对当前部署基线的全库门禁。当前部署基线是无技能。门禁要求至少两个独立来源各自在两轮都改善，改善伴随技能使用变化，且无观察到的退化。此前的 2/6 和人工 6/6 用于说明来由，不能充当新一轮的配对分母。原对象开发题已被反复观察，成功时仍需区分面板内改善与新来源迁移。

在首个子版的对象对照中，正常路由下父版 4/6、子版 5/6。唯一多修好的一次发生在记录索引题上，双方都跳过技能，首次求解请求哈希相同。强制注入时父子都是 3/6，一胜一负。配置题则出现了重复改善，子版 8/8，父版 6/8，无技能 3/8。CSV 标题相对父版连续两轮改善，CSV 标题和采样间隔相对无技能都连续两轮改善。支持集回放时，子版可用的那组漏修了一次租约题，该次实际路由也跳过了子版。发布门禁保留这次退化。[逐配对评分与门禁](results/object-revision.json)

| 原对象面板中独立通过的修复 | 首个子版实验 | 加入配对断言的子版实验 |
| --- | ---: | ---: |
| 无技能 | 5/6 | 4/6 |
| 父版，正常路由 | 4/6 | 4/6 |
| 子版，正常路由 | 5/6 | 5/6 |
| 强制父版 | 3/6 | 3/6 |
| 强制子版 | 3/6 | **6/6** |
| 人工参照 | 6/6 | 5/6 |
| 正常路由实际注入子版 | 1/6 | **4/6** |

在第二项实验的标签回调题上，强制父版两轮都交付了通过公开测试与常规输入的补丁。两份补丁也都在空批次和非空批次上丢弃了调用方提供的假值回调。强制子版两轮都通过这两条独立断言与整题评分。第三个强制组胜例出现在空结果容器的第二轮，父版丢失空批次最终写入的目的对象，子版保留了它。三个胜例都有实际补丁可复验。[逐补丁行为检查](results/object-witness.json)

正常路由下，标签回调题是唯一连续两轮由父版失败变为子版通过的来源，子版两轮均实际注入。结果容器上父子两轮都修好。异常对象上新子版两轮都未被选用，一次路由响应格式无效，一次主动跳过，第二轮出现父版通过、子版失败。三个来源中只有一个满足重复改善，门禁要求至少两个。

原配置题也揭示了范围修订的代价。在第二项实验的八次配置求解中，无技能修好 **4/8**，父版修好 **6/8** 且注入 **8/8** 次，新子版修好 **3/8** 且注入 **0/8** 次。采样间隔首轮的路由记录说明，模型把题面识别为“恢复缺失的默认值”，认为它未表明调用方提供的对象遭到真值判断丢弃。在这个面板上，新规则覆盖了更多对象入口，先前的配置入口却全部被跳过。[各题路由说明与评分](results/object-witness.json)

第二个子版的八道学习证据回放均通过，包括触发修订的租约学习题。父版同样通过八道，无技能通过五道。完整正常父子门禁保留了采样间隔、调色板和异常对象三个来源上的退化。对无技能的全库比较也保留了调色板和异常对象上的退化。两次实验均未激活候选。两份实验状态库和共用暴露账本中，这 30 道封存题的模型运行数与接触题数均为 **0**，没有可绘制的多样性收益观测点。原留出组划分为单值、多层和批处理三个配置族，未来的该组曲线衡量配置任务多样性，未见调用方对象的迁移仍需独立样本。

首个子版实验使用 **877 次 GLM 调用**，估算 **859.26488 套餐积分**。补充实验新增 **848 次调用、859.45601 积分**，已计入三次断言草案和两次技能提案。两项合计 **1,725 次真实调用、1,718.72089 估算积分**。两份费用收据的待结算预留均为零。两个子版共用的历史学习轨迹按原运行 ID 引用，补充实验没有再次为这些学习调用计费。[首轮账目](results/object-revision.json) · [补充账目](results/object-witness.json)

## 怎样复核

仓库中的公开记录可离线重算，包括提案与证据的绑定、正常与强制用法、逐题门禁和各组账目。原始模型会话与 SQLite 账本留在本地。安装 Docker 并准备好 `python:3.12-slim` 后，可以在干净副本重现六道学习题的校准，以及模型所写断言在两个提交和参考修复上的结果。以下命令均无需模型密钥。

```bash
uv run --locked python scripts/report_object_revision.py verify
uv run --locked python scripts/report_object_revision.py verify --study witness
uv run --locked python scripts/report_object_revision.py calibrate
uv run --locked python scripts/report_object_revision.py replay --study witness
uv run --script docs/results/plot.py
```

带有本地原始归档的环境还可以用 `export` 将每块提交的补丁重新装入冻结镜像，重跑各项对象边界检查，再从两份状态库和共用账本核对是否接触留出题。真实模型的重复运行可能产生不同的补丁。

真实重跑需要国内智谱 Coding Plan 配置、原父版学习归档、前次对象面板归档和相同镜像。首轮提案策略也可从项目的 `evocoder propose --proposal-policy grounded_scope` 入口使用。两次登记提交均早于各自的首个模型调用，补充组只在首个子版完成门禁并保持留出封存后启动。[首轮登记提交](https://github.com/Phoenix-chaser/EvoCoder/commit/6ff21398cc2e4fad47ab3b2551ff66f45294b8c8) · [补充组登记提交](https://github.com/Phoenix-chaser/EvoCoder/commit/5b2f59971b34666078d7f514984d049c872194c0)
